# 武俠合成／和風合成（gousei）簡易版 設計書

日期：2026-10-16
狀態：使用者已同意設計，待審閱本文件。

---

## 1. 目標與範圍

新增小遊戲「武俠合成」：玩家從初始物體開始兩兩合成，先合出自己全部任務物的人獲勝。

本設計只涵蓋**簡易版**（事前產生的合成表）。

範圍外：

* 使用 Yahoo! JAPAN 文字解析 API 的進階版（需要中繼伺服器與 AppID 保管，另立設計）。
* 裝置間同步（Firebase）。

---

## 2. 主題

| 主題 | id | 初始物體（階段 0） |
| --- | --- | --- |
| 中國武俠風 | `wuxia` | 金、木、水、火、土 |
| 日本和風 | `wafu` | 火、水、雷、風、土 |

每個物體都有 `zh` 與 `ja` 名稱；`en` fallback 至 `ja`（與其他遊戲資料一致）。

規模：**每個主題 5,000 種以上，兩主題合計 1 萬種以上**。

## 4. 資料模型

### 4.1 物體

```text
[id, zh, ja, category, tier]
```

* `id`：主題內唯一的短字串。
* `category`：分類 id（例如兵器、武學、人物、門派、自然、器物、丹藥⋯），各主題自訂，分類名稱也有 zh/ja。
* `tier`：階段，由 `build.py` 計算，不手寫。

### 4.2 配方

* key：`"a|b"`，`a`、`b` 依 id 排序（`a <= b`），允許 `a === b`（同物體自我合成）。
* value：結果物體 id。
* 一個 key 只能對應一個結果（決定性）；一個物體可以有多條配方。

### 4.3 階段計算

```text
tier(初始物體) = 0
tier(c) = min over 配方 (a,b→c) of ( max(tier(a), tier(b)) + 1 )
```

以 BFS／固定點迭代求得。無法從初始物體到達的物體視為錯誤。

### 4.4 廢料（必定有結果）

* 每個主題另備約 20 種**廢料**物體（例如灰燼、碎石、廢鐵⋯），分類為 `junk`。
* 配方表沒有的組合 → 依組合 key 的確定性雜湊挑一個廢料。
* 任一邊是廢料的組合一律產生廢料（廢料不能當作通往任務的捷徑）。
* 廢料也會進入共用池子。

## 5. 遊戲規則

### 5.1 設定

選擇：主題、人數（2〜8）、玩家名稱、模式（同一裝置／分別裝置）。開始時產生 `seed`。

### 5.2 發任務

以 `seed` 的確定性亂數為每位玩家發 3 張任務：

* 中階 ×1：階段 3〜4。
* 高階 ×2：階段 5〜7。
* 全體玩家的任務不重複；不從廢料中抽。

### 5.3 提示

任務卡只顯示**物體名稱、分類與階段**，不顯示配方。

### 5.4 回合

* 共用池子：所有已發現物體全員共用；初始物體永遠在池子中。
* 依座位順序，每一輪每人合成**一次**（從池子選兩個物體）。
* 合成結果加入池子（若是新物體），並記錄於合成紀錄。

### 5.5 達成與勝利

* **只有在自己的回合親手合出自己的任務物才算達成**；別人先合出、已在池子中的不算。
* 達成時全員可見「○○ 達成 2/3」（不公開是哪一張）。
* 最先達成全部 3 張的玩家立即獲勝。

### 5.6 兩種模式

| 模式 | 合成 | 查看任務 |
| --- | --- | --- |
| 同一裝置 `shared` | 共用裝置 | 每回合開頭顯示「請交給 ○○」遮蔽畫面，點擊顯示／隱藏自己的任務 |
| 分別裝置 `split` | 共用裝置 | 共用裝置顯示參加 QR／代碼（含 seed、主題、人數、玩家編號）；各自手機開啟後只顯示自己的任務。不同步，手機只是看任務用 |

分別裝置模式下，共用裝置仍能由 seed 算出全員任務，用於自動判定達成，但不顯示內容。

### 5.7 UI 輔助

* 池子可搜尋（zh/ja 名稱）與依分類篩選。
* 合成紀錄（誰、哪兩個、得到什麼、是否新發現）。
* 可復原上一次合成（只保留一層，與 utau 相同）。

## 6. 資料製作流程

1. 先為每個主題定義分類清單與階段骨架（每分類大約的數量與階段分布）。
2. 依分類由平行代理產生原始 JSON（物體 + 配方）。配方以「從名稱就能聯想」為最高原則，因為玩家只有分類與階段可參考。
3. `build.py` 驗證並修正至通過：
   * 名稱重複（同主題內 zh 或 ja 重複）
   * 配方引用不存在的物體
   * 同一 key 對應多個結果
   * 無法從初始物體到達
   * 階段分布：階段 3〜4、5〜7 的物體數量足夠發任務（每階段帶至少數百種）
   * 物體總數 ≥ 5,000（每主題）
4. 輸出精簡格式的 `gousei_data_<theme>.js`。

---

## 7. 驗證

* `node --check` 所有新增 JS。
* `tools/gousei_check/core_check.js`：合成決定性、廢料規則、發任務不重複且階段正確、同 seed 結果相同、達成／勝利判定、復原。
* `python tools/gousei_data/build.py`：資料驗證全部通過。
* `python generate.py` 後以 Playwright 跑一次兩種模式的完整流程。
