# midnight 戰鬥 sprite 動畫層 設計文件

日期：2026-09-21
對象：`static_src/midnight.js`（即時制）／`site_src/midnight_page.py`／新增 `tools/sprite_*`
關聯文件：`docs/midnight_realtime_combat_numbers.md`（現行戰鬥數值與判定的權威紀錄）

---

## 1. 背景

現行 midnight 即時制戰鬥的敵人表現是「HUD 下方中央的一張靜態插圖」
（`#midnight-field-encounter-image`，圖源 `static_src/images/enemies/*.jpg`，149 張規則書插圖）。
攻擊的反應判定與畫面表現完全脫鉤：

```
enemyAttack 產生 → ⚠ 閃爍 0.5 秒（ENEMY_ATTACK_WARN_MS）
                 → 反應窗口 2.0／2.5／3.0 秒（ENEMY_ATTACK_HIT_WINDOW_MS）
                 → 窗口內按過迴避／防禦 = 成功，沒按 = 命中
```

見 `updateMyIncomingAttack()`（midnight.js:8953）。這個結構有三個已確認的問題：

1. **迴避嚴格優於防禦**：迴避固定 10 體力且完全無效化，防禦要付「骰子數×2」體力卻只有
   百分比減傷。除了想觸發「防禦成功時」系的遺物／詞條，理性玩家永遠按迴避。
2. **沒有時機可言**：2~3 秒窗口內「按過就算」，且防禦是長按、按著不放即自動成功，
   操作精度與風險都不存在。
3. **招式名稱讀了沒有用**：`#midnight-incoming-attack-name` 特地做成不閃爍以便閱讀
   （見既有文件 §13.5），但讀完之後最佳應對永遠是同一個按鈕。

## 2. 目標與非目標

### 目標

- 敵人從靜態圖變成有動作動畫的 2D 實體（點陣圖 sprite）。
- 不同招式播放不同的攻擊動畫，玩家依動畫判讀命中時機按下迴避。
- 迴避帶實際方向位移，接上既有的地圖座標。

### 非目標（本設計明確不做）

- 不改規則書的傷害計算鏈（`resolveEnemyActionOutcome()`／`applyDamageToFieldEnemyHp()` 等）。
- 不動 `night.js`（回合制）——兩套系統本來就各自獨立。
- 不做玩家角色的 sprite（本輪只處理敵人側）。
- 招式分類**不產生規則分歧**，只用來決定播哪一個動畫。

## 4. 架構：三層解耦

```
資料層   動作時間軸 metadata ＋ 招式→動畫對照表     （不含美術）
表現層   sprite renderer（缺圖自動 fallback 現有靜態圖）
判定層   命中幀 × 無敵幀                            （不碰圖）
```

**這是本設計最重要的約束**：判定層只讀 metadata 的 `hitFrame`，永遠不接觸圖片本身。
因此：

- sprite 尚未產出時遊戲照常運作（走 fallback），管線不會阻塞玩法開發。
- 日後若要整批替換美術風格，判定與規則一行都不用改。

### 4.1 sprite 與原插圖的疊放（2026-09-21 使用者明確規格改版）

初版是「sprite 取代原插圖」（顯示 sprite 時把 `<img>` 藏起來）。改為**兩者並存**：

> 背景仍舊顯示元圖片，產生的點陣圖敵人顯示在圖片的頂層。

- `#midnight-enemy-sprite-stage` 改成 `position: absolute` 疊在 `<img>` 正上方，
  `width: 100%` ＋ `aspect-ratio: 1 / 1`，跟著插圖的實際渲染寬度縮放。
- **不指定 `z-index`**：`#midnight-field-encounter-image-wrap` 裡的 DOM 順序本來就是
  舞台（`mount()` 插在 `firstChild`）→ `<img>` → `#midnight-enemy-hit-effect` →
  `#midnight-enemy-ailment-effect`。`<img>` 沒有定位、舞台有定位，所以舞台必定畫在插圖
  之上；兩個特效同樣有定位且 DOM 在後面，所以仍畫在舞台之上——刀光與屬性光暈本來就
  應該蓋在敵人身上，這個堆疊順序剛好就是要的。
- 舞台加 `pointer-events: none`，純表現層不攔截點擊（例如逃離戰鬥按鈕）。
- 呼叫端（`renderFieldEncounterPanel()`）在 sprite 顯示成功時**不再動 `<img>.hidden`**。
  夜王分支對 nameless（名冊無立繪）刻意隱藏 `<img>` 的既有邏輯保持不變——那種情況下
  畫面上就只會有 sprite。
- 副作用：舊版把舞台寫死 420px 是因為「sprite 顯示時 `<img>` 被藏起來，inline-block
  父層寬度會算成 0」。插圖既然一直留著，這個理由消失，改用 `100%` 同時解掉舊版
  「舞台固定 420px 而非跟著圖片縮放」的已知落差（FINAL 輪 parked 的 minor），
  手機版也不再需要另外指定 45vw。

## 5. 素材規格

### 5.1 組數

依 `enemies_data_1~4.js` 實際資料：**25 個系統、149 隻一般敵人**（size 分布 LL 21／L 46／M 71／S 11），
夜王 10 隻。

| 類別 | 組數 |
| --- | --- |
| 一般敵人 | 25 系統 × 2 變體 = 50 |
| 個別敵人專屬（2026-09-23 追加） | 14 |
| 夜王 | 10 |
| 夜王的形態別（2026-09-22 追加） | 2（gladius 分裂／harmonia 第二形態） |
| **合計** | **76** |

**個別敵人專屬 sheet**（2026-09-23）：系統 sheet 是「一張代表整個系統」，但部分敵人
已另外畫了自己的圖，此時用 `enemy_<familyId>_<enemyId>`。`sheetIdForEnemy()` 在專屬圖
**已產出**時回傳它，否則退回系統 sheet——與 `sheetIdForBoss()` 的形態別同一個作法。
系統 sheet 仍是該系統所有成員（含已有專屬圖者）的代役來源，因此成員一覽不從這裡扣除。

只有在「系統 sheet 已經是別隻敵人的絵」時才開專屬 sheet。若該敵人是變體的唯一成員，
或變體尚未產出，直接把絵放進系統 sheet——否則同一張絵會存兩份，而且系統 sheet 會變成
沒有任何敵人引用的死檔。清單寫在 `sprite_registry_gen.js` 的 `ENEMY_OWN`。

**形態別 sheet**（2026-09-22 使用者明確規格「確保有些敵人會有不同型態，產生兩種以上點陣圖」）：

多形態的夜王在第二形態時外型完全不同，因此各多給一張 sheet。既定形態沿用 `boss_<id>`，
第二形態為 `boss_<id>_split`（接尾辭就是 `state.battle.bossForm` 的值，harmonia／nameless
這種語意上是「第二形態」的也用同一個字，只是讓登錄表的鍵跟 bossForm 對齊）。

**哪些夜王真的要第二張圖**（2026-09-22 使用者明確規格）：戰鬥規則上的多形態（`formAware`）
有 4 隻，但實際畫第二張的只有 **gladius**（合體⇄分裂）與 **harmonia**（第二形態是分身）。
**stragedes／nameless 的形態變化只在後台**，畫面仍用第一形態的圖——`sheetIdForBoss()` 會
回傳既定 sheet，所以不用在程式裡另外分支。產生器的 `BOSS_FORM_ART` 記這兩隻。

**形態別的體數**（同上規格）：分裂不是換一張圖而已，還要改變「畫面上有幾隻」。

| 夜王 | 形態 | 體數 |
| --- | --- | --- |
| gladius | 合體 | 1 |
| gladius | 分裂 | **3**（橫排三隻單頭犬） |
| harmonia | 第一形態 | 1 |
| harmonia | 第二形態 | **9**（分身） |
| 其餘 | — | 1 |

表現層 `showSprite(file, prefix, count)` 會把舞台切成 count 份：5 隻以內橫排一列，
超過就排成兩段（9 隻＝後列 4＋前列 5，後列上移並向中間錯開）。全員同一幀、下端對齊。

**形態變化的最短持續 30 秒**（同上規格）：gladius 的「炎突進＆形態変化」每次抽中都會
翻轉形態，連續抽中時畫面會在 3 隻⇄1 隻之間抽搐。`BOSS_FORM_MIN_HOLD_MS = 30000`，
距上次變化未滿 30 秒就維持原形態（招式照常發動、傷害照常計算，只有形態與外觀不變）。
變化時刻記在 `fieldTrigger.bossFormChangedAt`，跟形態本身一樣全端共享——存在各端本地的話，
不同人看到的體數會不一樣。

登錄表的 `sheetIdForBoss(bossId, form)` 只在專用 sheet **已產出**時才回傳它，否則退回
`boss_<id>`——同一個夜王的另一個形態，總比代役（別的夜王）接近。

### 5.2 「每系統 2 組」的切分規則

- 系統內 size 有明顯落差者，依體型切「大／小」兩組。
  例：岩獸・靈獸系（L×3／LL×3）、甲殼類系（LL×2／L×2／M×1）。
- 系統內 size 全部相同者，切為兩種外觀變體，避免十幾隻長相完全一致。
  例：士兵・騎士系（18 隻全 M）、鬥士・劍士系（12 隻幾乎全 M）。

哪一隻敵人用哪一組，存成明確的對照資料，不在程式裡用猜的。

### 5.3 sheet 規格

| 項目 | 值 |
| --- | --- |
| 動作 | 待機／直線／範圍／突刺／重砸／單擊／受擊／死亡 |
| 幀數 | 6 幀／動作 → 48 幀／組 → 全體約 2,880 幀 |
| 佈局 | 單張 sheet，橫 6 幀 × 縱 8 動作 |
| 單格形狀 | 正方形為原則，橫長亦可（見下方「非正方形的單格」） |
| 第 1 格 | 每行最左格只畫前搖，不畫招式圖（見 §5.5） |
| 朝向 | 一律繪製朝左，朝右以 CSS `scaleX(-1)` 翻轉 |
| 背景 | 透明 PNG |
| 命名 | `family_<familyId>_<a\|b>.png` ／ `enemy_<familyId>_<enemyId>.png` ／ `boss_<bossId>.png` |

單格尺寸與色階由第一組實圖回頭校正後定案（見 §10 階段 2），規格文件 `tools/sprite_spec.md`
為生成端與驗收端的共同依據。

體積預估：128×128 單格時每組 sheet 約 768×1024，60 組約 12~24MB，與現有
`static_src/images/enemies`（22MB／149 張）同量級，可接受。

**非正方形的單格（2026-09-22 使用者明確規格「分裂形態不用正方形沒關係、保持原圖尺寸」）**

生成物的 8 行高度不一定相等。以往是切成正方格再統一，但那會迫使畫面縮放或裁切；改成
**按實際的行界線切、各幀高度不同也照切，最後以底部為共同基準對齊**（`sprite_sheet_relay.js`
的 `--rows=detect --cell=fit`）。單格因此可能是橫長的（gladius 分裂形態實測 280×160）。

表現層不需要任何 metadata：`midnight_sprite.js` 的 `cellAspectOf()` 直接由載入後的圖片實寸
算出「1 格的高÷寬」（`naturalHeight/8 ÷ naturalWidth/6`）。登錄表不記縱橫比——記了就會跟
圖片變成兩份資料，換圖時必有一邊過期。

舞台本身維持正方形（疊在插圖上的位置不變），真正貼圖的是舞台內一塊「1 格高度」的面，
貼齊舞台下緣。這樣橫長單格不會讓上一行的絵露出來，而且接地位置跟正方形單格完全一致。
`sprite_verify.js` 因此不再要求正方形，只要求能被 6×8 整除，且單格縱橫比落在 0.4~2.5
（超出這個範圍多半代表「用 6×8 去切」這個前提本身就錯了）。

### 5.4 metadata

每組附一份 JSON，逐動作記錄：

```
{ "frameCount": 6, "fps": <n>, "hitFrame": <index>, "recovery": <ms> }
```

`hitFrame` 是判定層唯一關心的欄位。

### 5.5 每行第一格＝前搖（2026-09-21 使用者明確規格）

> 各行的第一個要為前搖動作而不出現招式圖。

第 1 格（index 0）只畫蓄力姿勢，不得出現刀光／殘影／飛行道具／光束／魔法陣／衝擊波／
揚塵／命中閃光。招式圖從第 2 格起，在第 4~5 格達到最大。待機行的第 1 格為中立站姿，
受擊／死亡行的第 1 格為身體尚未反應的前一瞬間。

這條規則直接服務 §8.1：`hitFrame` 是 3~4，第 1 格必定在前搖之中，玩家就是靠它決定要不要
按迴避。第 1 格若已經畫出招式，看起來就像已經命中，讀招的時間等於沒有。

落地位置（兩邊成對，缺一邊就會各走各的）：

- 生成端：`tools/sprite_check/sprite_prompt.js` 的 `FRAME_RULE`，併入畫風契約與動畫表指示；
  已在跑的對話用 `--format=frame-rule` 單獨補這一條。
- 資料端：`tools/sprite_check/sprite_anim_check.js` 檢查 5 種攻擊動作的 `hitFrame` 不為 0。

## 6. tools/ 管線

沿用既有 `tools/`（`field_card_sweep`／`midnight_check`／`night_check`）的工具腳本慣例。

工具一律是 **Node 腳本**，放在 `tools/sprite_check/`，以 `package.json` 的 npm scripts 註冊
（`generate.py` 是專案裡唯一的 Python；`tools/` 既有的 `midnight_check`／`field_card_sweep`
都是 Node）。**不新增任何 npm 相依。**

| 工具 | 職責 |
| --- | --- |
| `tools/sprite_spec.md` | 規格本文 |
| `sprite_prompt.js` | 讀 `enemies_data_1~4.js`，依系統名稱／size／代表招式產生每組的生成 prompt |
| `sprite_registry_gen.js` | 產生 sheet 登錄表與 149 隻的歸屬 |
| `sprite_action_map_gen.js` | 招式關鍵字自動對應，並列出未命中的長尾名稱供人工補標 |
| `sprite_verify.js` | 匯入檢查：命名在登錄表內、合法 PNG、寬高可整除為 6×8 正方格 |
| `sprite_pack.js` | 把通過驗收的 sheet 在登錄表標記為 `available: true` |

**不切幀**：renderer 以 CSS `background-position` 直接從 sheet 取單幀，因此不產生切好的單幀
檔，`sprite_pack.js` 只更新旗標。驗收只需讀 PNG 的 IHDR 取寬高，零相依即可完成。

**圖片生成本身在專案外部執行**（開發環境沒有圖像生成能力）。管線的職責是讓產出物
「進得來、驗得過、接得上」，並在缺圖時不影響遊戲運作。

## 7. 招式 → 動畫對應

### 7.1 資料實況

`enemies_data_1~4.js` 共 **549 筆招式**、**430 個相異招式名**。關鍵字粗掃約可命中一半，
其餘落在長尾（例如「群がる」18 筆、「掴みかかり」10 筆、「飛びかかり」5 筆、「回り込み」3 筆，
字面推不出該播直線或範圍）。

### 7.1.5 夜王的招式（2026-09-22 追加）

夜王的 69 招原本完全不在對照表裡——產生器只讀 `enemies_data_*.js`。實際跑起來全部退回
`dmgKind` 預設（亂戰→範圍、個別→單擊），等於 sheet 上的直線／突刺／重砸三行幾乎不會播。

改成產生器同時讀 `night_boss_rulebook.js`，並且**每隻夜王各持一張獨立對照表**（`BY_BOSS`）：
招式名會跟一般敵人重複（噛みつき、突進等），混在同一張表裡動一個就會波及另一邊。
`resolve(actionName, dmgKind, bossId)` 先查該夜王的表，再查共用表，最後才退 `dmgKind`。

每隻的分配方式（使用者明確規格「先分析第一波，安排相應動畫，剩下不好分的可以直接由還沒有
被選中的動畫隨機挑選；這樣就能保持全部動畫都有機會登場」）：

1. 先用關鍵字表／`OVERRIDES` 決定能決定的；
2. 還沒出場的動畫，依招式在表上的順序分給尚未決定的招式；
3. 若仍有動畫沒出場，從「同一動畫被分到兩招以上」的招式裡讓一招出來。

**不使用亂數**——在產生時決定並寫死進對照表，全端末、全場次必須一致。結果是 10 隻夜王
各自都用滿 5 種攻擊動畫（`sprite_action_map_check.js` 會逐隻檢查）。

### 7.2 對應流程

1. 關鍵字表自動對應：
   - 突き／突進 → 突刺
   - 薙ぎ払い／振り回し → 範圍
   - 叩きつけ／跳躍／落とし → 重砸
   - 射撃／つぶて／放つ → 直線
   - 噛みつき／爪／ひっかき → 單擊
2. `tools/sprite_action_map.py` 列出未命中的相異名稱（估 130~180 個），一次人工補標。
3. 結果存成 `static_src/enemy_action_anim_map.js`（相異招式名 → 動畫 id）。
4. 漏標時依既有 `dmgKind` 退回預設（個別傷害→單擊、亂戰傷害→範圍），不開天窗。

對應是**依相異招式名**而非依 549 筆，補標為一次性工作。

## 8. 判定改為動畫驅動

### 8.1 新時序

```
動畫前搖 0.4~0.7 秒（可讀）──→ hitFrame ──→ 後搖
玩家按下迴避 → [ 無敵幀 0.25 秒 ]
無敵幀覆蓋 hitFrame = 迴避成功（完全無效化）
未覆蓋                = 迴避失敗，套用 30% 減傷後受傷
```

- 前搖長度依動作種類在 0.4~0.7 秒之間取值（重砸較長、單擊較短），確切分配寫入 metadata。
- 迴避失敗的 30% 減傷是**新的一層**，與既有的防禦百分比減傷、暫時減傷、隊伍減傷各自獨立，
  插入位置比照既有慣例（見 `resolveMyIncomingHit()` midnight.js:9067 的減傷層順序）。
- 防禦（長按）維持現行行為，成為「好按但只有部分減傷」的保險選項。迴避改為
  「時機準才完全無效化、不準仍有 30% 減傷」的高報酬選項——原本「迴避嚴格優於防禦」的
  失衡由此消解，且不需要削弱迴避的報酬。

### 8.2 時鐘偏移風險（重要）

`static_src/game_storage.js` 目前**完全沒有處理時鐘偏移**（無 `serverTimeOffset`、
無 `ServerValue.TIMESTAMP`）。現行 2~3 秒窗口下，裝置間 200~300ms 的時鐘差無關緊要；
但無敵幀只有 0.25 秒時，時鐘偏移會直接造成「某位玩家怎麼按都躲不掉」。

對策（兩者都做）：

1. **判定以本地觀測到的動畫起始時刻為基準**往後推算 hitFrame，而不是拿共享的
   `enemyAttack.warnAt` 絕對時間直接與本地 `Date.now()` 比對。
2. 接上 Firebase 的 `/.info/serverTimeOffset` 做校正，供需要絕對時間的場合使用。

不新增任何 RTDB 同步欄位——所有客戶端由既有的共享 `enemyAttack` 記錄加上動畫 metadata
即可推出同一個 hitFrame。

### 8.3 判定優先序與「失敗」的定義

同一擊的判定優先序維持現行的 迴避 > 特殊防禦 > 防禦（見 `updateMyIncomingAttack()`），
只把「迴避成功」的定義換成「無敵幀覆蓋 hitFrame」。由此衍生的三種結果必須明確區分：

| 玩家行為 | 結果 |
| --- | --- |
| 按下迴避，無敵幀覆蓋 hitFrame | 迴避成功，完全無效化（同現行） |
| 按下迴避，無敵幀未覆蓋 hitFrame | 迴避失敗，套用 30% 減傷後受傷 |
| 完全沒有按迴避 | 全額受傷（同現行 `kind === "hit"`） |

亦即 30% 減傷是**「有嘗試迴避」的獎勵**，不是所有受擊的通用減免——按了但時機不準優於完全不按。

迴避失敗時體力照扣（維持 `dodgeStaminaCost()` 現行成本與「華麗身法」減免）。
迴避未覆蓋 hitFrame 時不視為已迴避，因此若玩家同時正長按防禦，該擊改走既有的防禦分支
（百分比減傷），不與 30% 疊加。

### 8.4 2026-09-22 使用者規格改版（取代 §8.1 的無敵幀設計，已實作）

§8.1 的「無敵幀 0.25 秒覆蓋 hitFrame」未實作即被使用者的明確規格取代。實作見
`midnight.js` 的 `SPRITE_DODGE_*` 常數群、`spriteHitAt()`／`scheduleSpriteHit()`／
`spriteDodgeReducePct()`／`showDodgeGrade()`，只在 `meta.spriteMode` 的房間生效；
非點陣圖房與反擊（`isCounter`）維持舊規則（2.0/2.5/3.0 秒、窗口內按下＝100%）。

```
warnAt ──紅光 0.5s──▶ T(0)（正式出招）
   T(k)−0.1s        sprite 從 idle 切成攻擊動畫；連擊每一下各重播一次（maybePlayEnemyAttackAnim）
   [T−0.1s, T+0.35s]  Perfect 100% 減傷
   (T+0.35s, T+0.5s]  Great   99→90%（帶內線性）
   (T+0.5s, T+0.8s]   Good    89→60%
   (T+0.8s, T+W]      Bad     59→30%；W = 1.0／1.5／2.0s（第 1／2／3 下，＋轉身之步 0.2s）
   （時間帶固定、不隨 W 伸縮；2026-09-22 第 3 版「判定嚴格度更改」，取代第 1 版
   「T+0.2 後整段線性 100→30」與第 2 版「0.3／0.5／0.75、99→80／80→60」）
   早於 T−0.1s 按    不算（體力照扣）；完全沒按 → 全額受傷
   T(k+1) = T(k) + W(k)；紅光只在第 1 下前顯示
```

- 成功度顯示（迴避鍵上方、與「成功迴避」並列，1 秒後消失）：依按下時刻所在的時間帶決定
  Perfect／Great／Good／Bad（`SPRITE_DODGE_BANDS`／`spriteDodgeJudge()`），不由減傷％反推。
- 不滿 100% 的迴避走 `kind === "dodgePartial"`：減傷是獨立的一層乘法（放在 block 百分比同一位置、
  互斥），屬性／異常蓄積比照命中承受（§8.1「迴避失敗＝受傷」的定義不變）。
- 動畫排程與判定共用 `spriteHitAt()`，窗口長度含只有自己知道的遺物加成，因此各裝置自己算、
  不新增 RTDB 欄位（§8.2 的原則不變）。動畫的 hitFrame 目前純屬演出，不參與判定。
- 回歸測試：`tools/midnight_check/sprite_dodge_check.js`。

## 9. 方向性迴避

- 迴避時依目前的移動輸入方向（WASD／搖桿）產生實際位移；無方向輸入時預設後退。
- 位移後夾在遭遇判定半徑（`FIELD_TRIGGER_RADIUS = 1.6`）內，避免一次迴避就意外脫離戰鬥。
- 現行 `handleDodgeClick()`（midnight.js:7347）只扣體力與記時間戳，角色完全不動，
  本設計為其加上位移；體力成本與既有的「華麗身法」減免維持不變。

## 10. 分階段交付

| 階段 | 內容 | 驗收 |
| --- | --- | --- |
| 1 | 規格 ＋ tools 管線 ＋ 遊戲端 renderer ＋ fallback | 畫面完全不變，管線可用，缺圖不影響遊戲 |

## 11. 風險

- **生成風格一致性**：60 組必須看起來屬於同一個世界，且與既有規則書插圖的畫風並存不突兀。
  由 `sprite_prompt.py` 統一 prompt 骨架，並在階段 2 先驗證。
- **行動裝置效能**：48 幀 sheet 的播放與多層既有特效（刀光／屬性光暈／丟擲物）並存。
- **hitFrame 與體感落差**：視覺上的「打到」與資料上的命中幀未必一致，需於階段 2 實測校正。
- **時鐘偏移**：見 §8.2，已有對策但需實機驗證。
