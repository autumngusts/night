# 東正小遊戲（toushou） 設計規格（第 1 階段：單機傳遞模式）

日期：2026-10-15
狀態：已與使用者確認，待審閱

---

## 1. 目標與範圍

在首頁新增一個與「夜渡り」（night／midnight）完全獨立的派對遊戲「東正小遊戲（toushou）」。
玩家對多個「標的」（歷史事件、人名、公司行號、風景、物品等）秘密押注並**預測最終股價**，
再輪流擔任「股東」釋放消息面，由全場討論決定股價加減分，最後由預測最接近的人瓜分彩池。

### 1.0 設計重點：避免利益單向化

若只有「看漲／看跌」兩種押注，每個人的利益都是單向的（越漲／越跌越好），
擔任股東時必然一面倒地替自己的部位喊話。因此改為「猜價格＋彩池」：
每個人希望股價**停在自己預測的位置**，好消息講過頭也會傷到自己，
使消息面成為互相拉扯的博弈。另外提供可勾選的「風向卡」規則，強制消息方向。

### 1.1 分階段

| 階段 | 內容 |
| --- | --- |
| **第 1 階段（本 spec）** | 單機傳遞模式：一台裝置，主持人操作，需要保密的步驟以遮蔽畫面輪流傳遞 |
| 第 2 階段（另開 spec） | 多裝置連線模式：重用 `PriTestGameStorage.rtSet / rtSubscribe / rtTransaction`，把 action 寫到 `games/<id>/rtState/toushou` |
| 強化版（另開 spec） | 股東內線資訊、股東指定分數目標與專屬計分等 |

第 1 階段的狀態模型必須設計成「可序列化的單一 `state`＋純函式 reducer」，
讓第 2 階段只需把 action 改經雲端同步，不必修改規則邏輯。

### 1.2 基本版明確不做

- 股東的內線資訊（暗牌、真實風向）
- 股東專屬計分／獎懲
- 多裝置連線
- 出牌直接影響數值（消息牌僅供討論，數值一律由全場共識輸入）

## 2. 檔案結構

| 檔案 | 職責 |
| --- | --- |
| `site_src/toushou_page.py` | `build_toushou_html()`，使用 `layout.page_shell` 產生頁面骨架 |
| `static_src/toushou_data.js` | 純資料：標的池、消息牌表、任務卡定義、類別→角色名稱對照。掛載為 `window.PriTestToushouData` |
| `static_src/toushou.js` | 規則引擎（`reduce(state, action)`、結算、任務判定）＋畫面渲染。掛載為 `window.PriTestToushou` |
| `site_src/i18n_data_{zh,ja,en}.py` | UI 文字 key（前綴 `ts_`）及首頁 `project_toushou_name/desc` |
| `site_src/projects.py` | 新增首頁入口 `toushou/index.html` |
| `generate.py` | copy list 加入兩個 JS，`build_pages()` 輸出 `dist/toushou/index.html` |

不修改 night／midnight 的任何檔案，也不修改 `database.rules.json`。

規則引擎與渲染寫在同一個 `toushou.js` 內，但 reducer 與結算函式不得碰觸 DOM，
並在 `window.PriTestToushou` 匯出（`reduce`、`settleTarget`、`evaluateMissions`、`_debugState`），
以便 Playwright 直接驗證。

## 3. 開局設定（`setup` 階段）

| 項目 | 選項 |
| --- | --- |
| 玩家人數 | 2～10 人，可輸入名稱（預設「玩家1」…） |
| 初始籌碼 | 「全員一致」（輸入 1 個值，預設 1000）或「個別設定」（每人一個值） |
| 標的數量 | 「依人數」（＝玩家人數）或「自訂」（1～20） |
| 標的類別 | 勾選：歷史／人名／公司行號／風景／物品（至少 1 類） |
| 標的設定 | 「隨機產生」（從勾選類別的池中不重複抽取）或「手動輸入」（名稱＋類別＋標籤），可混用：先隨機，再逐一修改或替換 |
| 任務卡 | 啟用／不啟用 |
| 最低押注 | 整數，預設為初始籌碼的 10%（全員一致時）或 100（個別設定時），可修改 |
| 風向卡 | 啟用／不啟用（見 §4.3.2），預設不啟用 |

確定開局後：
- 每位玩家發 5 張消息牌手牌（牌堆洗牌；牌堆用完則把棄牌堆洗回）。
- 啟用任務卡時，每人秘密抽 1 張任務（不重複），以傳遞遮蔽方式逐人查看。

## 4. 一個標的的流程

### 4.1 抽出標的（`reveal_target`）
公開名稱、類別、2～3 個特徵標籤。起始股價固定 **100**。

### 4.2 全員下注（`bet`）
- 在任何消息釋放**之前**完成；確定後不可加碼或下車。
- 逐人遮蔽輸入：押注額 `B`＋預測最終股價 `P`（整數，≥ 0）。
- `B` 必須 ≥ 最低押注且 ≤ 目前籌碼；籌碼不足最低押注時只能全押（`B` = 目前籌碼）。
  有最低押注是為了防止「只押 1 籌碼卻猜中就拿走六成彩池」的漏洞。
- 籌碼為 0 的玩家本標的不參與押注（仍需擔任股東）。
- 確定時立即從籌碼扣除 `B`，放入本標的彩池。

### 4.3 輪流釋放消息（`news`）
- 系統以隨機順序排列全體玩家；本標的上**每位玩家各擔任一次**股東。
- 每一回合：
  1. 遮蔽畫面「請交給 ○○」→ 本人確認後顯示自己的手牌。
  2. 股東釋放一則消息，有三種方式（最終內容不可為空白）：
     - **直接打出手牌**：使用牌面上的固定消息。
     - **手牌轉自訂**：選一張手牌後按「改寫」，牌面文字會帶入輸入框，由股東自由修改成自己的版本。
     - **純自訂**：不用手牌，直接輸入消息。
     只要用到手牌（直接打出或改寫），該牌就進入棄牌堆，並立即從牌堆補 1 張。
  3. 公開消息，並把這則消息**掛到標的說明底下**（見 §4.3.1）。
  4. 其他人討論，由主持人輸入全場共識的**加減分**（整數，可為負或 0；啟用風向卡時受 §4.3.2 限制）。
  5. 股價 = max(0, 股價 + 加減分)，並寫入歷史紀錄。
- 角色名稱依標的類別顯示（僅為名稱，規則相同）：

| 類別 | 角色名稱 |
| --- | --- |
| 公司行號 | 股東 |
| 物品 | 黃牛 |
| 歷史／人名／風景 | 投資客 |

#### 4.3.1 標的消息面（累積說明）
- 每則釋放的消息（不論是固定牌面、改寫或純自訂）都依序累積在該標的的「消息面」說明中，
  與名稱、類別、特徵標籤一起顯示，用來持續形容這個標的，作為後續股東與全場討論的依據。
- 每則消息顯示：釋放者、內容、該次加減分、之後的股價（啟用風向卡時也顯示風向）。
- 消息面跟著標的保存在 `history` 中，標的結算畫面與整局結算畫面都能回顧。

#### 4.3.2 風向卡（開局可勾選）
- 股東回合開始時，先抽一張**公開**的風向卡：利多 2：利空 2：中立 1（風向卡為獨立牌堆，用 seed 洗牌，用完重洗）。
- 股東須依風向釋放消息（有符合方向的手牌可打出，沒有則自由發揮）。
- 加減分的正負由風向決定：利多只能輸入 ≥ 0，利空只能輸入 ≤ 0，中立不限。
- 下注仍是秘密的：大家看得到股東「被迫講利空」，卻不知道他預測的價位。

### 4.4 結算（`settle`）
- 彩池 = 本標的所有押注 `B` 的總和。
- 參與者（`B` > 0 的玩家）依誤差 `|P − 最終股價|` 由小到大排名。
- 分配比例依參與人數 n：

| n | 分配 |
| --- | --- |
| 1 | 100%（原數取回） |
| 2 | 第 1 名 100% |
| 3 | 70% / 30% |
| ≥ 4 | 60% / 30% / 10% |

- **同分**：誤差相同的玩家合併其名次的比例後平分（例如 n ≥ 4 時兩人並列第 1，合計 90% 平分，下一位為第 3 名拿 10%）。
- 金額一律無條件捨去成整數，捨去後的零頭給排名最前的玩家（並列時給座位順序最前者），確保彩池總額守恆。
- 顯示本標的明細：股價變化歷程、每人押注／預測價／誤差／名次／取回／盈虧。

然後進入下一個標的；全部結束後進入整局結算。

## 5. 整局結算（`final`）

- 最終分數 = 籌碼 ＋ 達成的任務獎勵。
- 依最終分數排名，並顯示每人的任務內容與是否達成、各標的的盈虧一覽。
- 提供「同設定再玩一局」與「回到設定」。

## 6. 任務卡（秘密目標）

只收錄**能從遊戲紀錄自動判定**的任務。資料格式：

```js
{ id: "m_bull_big", text: C(ja, zh), reward: 300, check: "bullWinAtLeast", params: { count: 2 } }
```

`check` 對應 `toushou.js` 內的判定函式表，判定只讀取 `state.history`（各標的的結算紀錄）與最終籌碼。
初版範例（約 8 張，獎勵與門檻為暫定值，可再調整）：

| 判定 | 內容 |
| --- | --- |
| `firstPlaceAtLeast` | 拿到第 1 名（含並列）的標的 ≥ N 個 |
| `exactHit` | 至少一次預測價與最終股價誤差 ≤ X |
| `categoryRiseAtLeast` | 指定類別中，有標的最終股價 ≥ X |
| `anyTargetCrash` | 有任一標的最終股價 ≤ X |
| `finalRank` | 最終籌碼（不含任務獎勵）為第 N 名 |
| `allInOnce` | 至少一次押注額 ≥ 當時籌碼的 80% 且獲利 |
| `contrarian` | 至少一次：過半數參與者預測的漲跌方向（P 相對於 100）猜錯，而自己猜對 |
| `ownNewsSwing` | 自己擔任股東時，有一次加減分的絕對值 ≥ X |

## 7. 資料

### 7.1 標的池
```js
{ id, category: "history" | "person" | "company" | "scenery" | "item", name: C(ja, zh), tags: [C(ja, zh), ...] }
```
每個類別先放約 10 個範例。手動輸入的標的存在 state 中（`custom: true`）。

### 7.2 消息牌
```js
{ id, text: C(ja, zh), tone: "up" | "down" | "neutral" }
```
`tone` 只作為畫面提示色。**正式牌表由使用者提供**；在此之前先放約 20 張標示「暫定範例」的牌（牌堆需能供 10 人 × 5 張開局手牌，不足時棄牌堆洗回）。

## 8. 狀態模型

```js
state = {
  version: 1,
  phase: "setup" | "reveal_target" | "bet" | "news" | "settle" | "final",
  config: { playerCount, chipsMode, targetCountMode, categories, missionsEnabled, ... },
  players: [{ id, name, chips, hand: [cardId], missionId }],
  deck: [cardId], discard: [cardId],
  targets: [{ id, category, name, tags, custom }],
  targetIndex: 0,
  current: {
    price: 100,
    bets: { [playerId]: { amount, predict } },
    pot: 0,
    order: [playerId],      // 本標的的股東順序
    turnIndex: 0,
    wind: null | "up" | "down" | "neutral",   // 啟用風向卡時，本回合的風向
    news: [{ playerId, cardId, edited, text, wind, delta, priceAfter }]   // 標的消息面；text 為最終公開內容，cardId 為 null 表示純自訂，edited 表示由手牌改寫
  },
  windDeck: [windId],
  history: [{ targetId, finalPrice, pot, news: [...], bets: {...}, ranks: { [playerId]: n }, payouts: { [playerId]: n } }],
  rngSeed: <number>
};
```

- 所有變更都經過 `reduce(state, action)`（純函式，回傳新 state），之後才 `save()`＋`render()`。
- 隨機性（洗牌、抽標的、股東順序）使用存在 state 中的 seed 驅動 PRNG，使 reducer 具有決定性（第 2 階段同步也需要此特性）。
- 存放於 `localStorage["pritest-toushou-state"]`，所有讀寫都包在 try/catch 中；讀到的 `version` 不符或格式錯誤時，捨棄並回到 setup。
- 提供「放棄本局」按鈕（需確認）。
- 傳遞遮蔽是 UI 狀態（`ui.revealedFor`），**不**存進 state，重新整理後回到遮蔽畫面。

## 9. 錯誤處理與邊界

- 押注額低於最低押注（籌碼足夠時）、超過籌碼、或非整數；預測價為負或非整數 → 停用確定鈕並提示。
- 籌碼為 0 的玩家仍需擔任股東，但跳過押注。
- 加減分輸入必須是整數，啟用風向卡時須符合風向正負；股價以 0 為下限。
- 全員籌碼皆為 0 → 直接跳到整局結算。
- 隨機產生標的但池中數量不足 → 抽完為止，並提示改為手動補足。
- 消息最終內容為空白（含把改寫的牌面文字刪光）→ 不可送出。

## 10. 驗證

1. `node --check static_src/toushou.js static_src/toushou_data.js`
2. `python generate.py`，用 `python -m http.server 8000 --directory dist` 手動遊玩一局。
3. 臨時 Playwright 腳本（不提交）：3 人 × 3 標的跑完一整局，讀取 `PriTestToushou._debugState()` 驗證：
   - 下注扣款、`settleTarget` 的彩池分配（n = 1/2/3/≥4、並列、零頭歸屬、彩池總額守恆）
   - 啟用風向卡時加減分的正負限制
   - 每個標的每位玩家恰好擔任一次股東
   - 出牌（含改寫）後手牌維持 5 張，純自訂不消耗手牌
   - 消息依序累積到標的消息面
   - 任務判定結果與手算一致
   - 重新整理後 state 完整還原
