## 1. 核心概念

山腳下沒落的小神社旁有一片荒地。玩家是回鄉的繼承人，在神社旁的老工房**製造遊樂設施與商品**，
把神社一步步經營成**一年四季都有祭典的樂園**。

```
工房生產零件／商品 → 組裝設施、上架商品 → 客人遊玩、消費、碎碎念（murmur）
       ↑                                               ↓
  擴張工房與樂園 ← 口碑・收入・人氣 ← 活動日・宣傳・四季祭典
```

主要樂趣：
1. **看客人玩**：3D 樂園中客人排隊、搭乘、吃東西、拍照；可以點選任一客人跟拍。
2. **murmur**：客人頭上冒出的碎碎念，是情報來源（抱怨＝問題點）也是氣氛。
3. **生產鏈**：工房把原料加工成零件與商品，餵給樂園。
4. **活動與擴張**：宣傳、活動日、季末祭典帶動人氣，解鎖土地與新區域。

## 2. 時間結構 📝

| 單位 | 長度 | 說明 |
|---|---|---|
| 年 | 4 季 | 春 → 夏 → 秋 → 冬 |
| 季 | 28 天 | 第 28 天為**季末祭典日** |
| 週 | 7 天 | 第 6、7 天為週末，客流 ×2 |
| 日 | 白天＋夜間 | 白天 9:00〜17:00；夜間營業需要解鎖（§7）並有足夠照明 |

* 一天的流程：**開園前**（規劃、配置、生產排程）→ **營業中**（即時，可 1×／2×／4× 速）→ **打烊結算**。
* 營業中可以暫停配置；設施建造在打烊後完成（大型設施需要多天）。
* 玩家可在行事曆加開「活動日」（§6.2）。

### 4.2 設施的共通數值

| 欄位 | 說明 |
|---|---|
| `capacity` | 一次乘載人數 |
| `cycleSec` | 一輪時間（秒，遊戲內時間） |
| `thrill`／`charm`／`photo` | 刺激度／可愛度／拍照度（對應客群喜好，§5.1） |
| `price` | 票價（可調；太貴降低滿意度） |
| `wear` | 每輪磨損；累積到 100 故障停擺 |
| `parts` | 組裝配方（零件 × 數量） |
| `level` | 1〜3；升級改變外觀、提升數值、需要額外零件 |
| `season` | 可營業季節；`night: true` 表示只在夜間營業 |

### 4.3 磨損與故障

* 每運轉一輪 `wear += wearPerCycle × (品質係數)`；劣質零件組裝的設施係數 1.5。
* `wear ≥ 100` → 故障，排隊客人產生「抱怨」murmur 並離開隊伍。
* 修理：消耗該設施的「替換零件」1 組＋維修時間。工房要保有庫存。

### 4.4 組裝配方範例

| 設施 | 零件 |
|---|---|
| 唐獅子旋轉木馬 | 彩繪木獅 ×12、黃銅柱 ×12、帆布頂棚 ×1、馬達 ×1、燈泡 ×40 |
| 燈籠摩天輪 | 鋼骨架 ×30、車廂 ×24、大型馬達 ×1、燈籠 ×120、漆 ×10 |
| 化け屋敷 | 木板 ×50、布偶 ×20、音響 ×2、機關裝置 ×6 |
| 天狗雲霄飛車 | 鋼軌段 × 軌道長度、列車 ×2、鏈條提升機 ×1、安全桿 ×24 |

## 5. 客人系統

### 5.1 客群 📝

| 客群 | 偏好 | 消費 |
|---|---|---|
| 親子 | charm、兒童區 | 餐飲多 |
| 情侶 | photo、摩天輪、夜景 | 商品中 |
| 學生團 | thrill、緣日攤位 | 低單價高數量 |
| 刺激派 | thrill | 票價不敏感 |
| 拍照派 | photo、季節設施 | SNS 發文率高 |
| 老人家 | 參拜、茶席 | 御守、和菓子 |
| 外國觀光客 | 和風設施、祭典 | 商品多 |
| 御宅族 | 合作 IP 活動 | 合作商品 |

### 5.2 需求值 📝

`fun`、`hunger`、`thirst`、`fatigue`、`toilet`、`photo`、`shopping`，各 0〜100。
* 隨時間變化；最高的需求決定下一個目的地（設施、攤位、長椅、廁所、拍照點、商店）。
* 某需求長時間無法滿足 → 滿意度下降，並產生「需求／抱怨」murmur。
* 滿意度過低或 `fatigue` 滿 → 離園。

### 5.3 客人的可見行為（3D）

| 行為 | 動作 | 狀態 |
|---|---|---|
| 走路 | 走路循環 | 🧪（看板人物 4 格走路動畫） |
| 排隊 | 站立、滑手機、跺腳 | 📝 |
| 搭乘 | 舉手、尖叫、閉眼 | 📝 |
| 吃東西／休息 | 坐在長椅 | 📝 |
| 自拍 | 舉手機 | 📝 |
| 買到限定商品 | 跳一下 | 📝 |

**跟拍**：點選任一客人 → 鏡頭跟隨，側欄顯示她今天的行程、需求值與 murmur 紀錄。📝

### 5.4 murmur（碎碎念）

| 類型 key | 範例 | 遊戲效果 |
|---|---|---|
| `impression` 感想 | 「摩天輪的燈籠好漂亮……」 | 顯示設施滿意度 |
| `complaint` 抱怨 | 「排隊排了 40 分鐘耶」 | 提示問題點（地圖上標記） |
| `need` 需求 | 「好想喝冷飲，附近都沒有賣」 | 提示攤位配置 |
| `recommend` 推薦 | 「下次要帶朋友來」 | 口碑 + |
| `sns` SNS 發文 | 「#緣日樂園 限定御守入手！」 | 宣傳效果 + |
| `gossip` 八卦 | 「聽說巫女小姐和工房的人……」 | 劇情伏筆 |
| `season` 季節 | 「今年的櫻花開得比較早呢」 | 氣氛 |
| `love` 戀愛 | 「他今天會不會告白呢……」 | 常客劇情 |
| `rival` 對手 | 「隔壁的樂園也開了新設施喔」 | 競爭事件提示 |

* 表示：客人頭上的氣泡（附小頭像）＋側欄的 **murmur 牆**（時間軸，可依類型篩選）。🧪
* 點氣泡 → 展開立繪與全文。🧪
* 文本：每種情境多組範本，填入 `{ride}`／`{item}`／`{weather}`／`{season}` 組出不重複的句子。📝
* **今日話題**：同一主題被 ≥ N 人提及 → 成為話題，影響隔天客流。📝

### 6.1 宣傳管道 📝

| 管道 | 成本 | 觸及 | 解鎖條件 |
|---|---|---|---|
| 發傳單 | 低 | 附近居民（親子、老人） | 開局 |
| 車站海報 | 中 | 學生、OL | 開局 |
| 地方報紙 | 中 | 中高年 | 人氣 Lv2 |
| SNS 官方帳號 | 低（效果看內容） | 年輕人 | 美羽好感 20 |

## 7. 工房與商品

### 7.1 工房 📝

* 格子配置的加工機＋輸送（簡化的自動化：機器 → 輸送帶 → 倉庫）。
* 加工機：製材、雕刻、沖壓、焊接、塗裝、繞線、燈泡爐、縫紉、射出成型、組裝台、刺繡、UV 印刷、雷射切割、火藥調合、蒸籠、搗餅台。
* 品質：原料 A／B／C；檢驗站把劣品分流。劣質零件影響設施磨損（§4.3）。
* 季節原料（神社祭典的部分）：櫻葉（春）、蠶繭（春夏）、新米（秋）、冰（冬，存冰室到夏天）。

### 7.2 商品 📝

1. **餐飲**：祭典小吃（章魚燒、炒麵、蘋果糖、棉花糖、刨冰）、和菓子、飲料、季節限定。
2. **原創商品**：基底 × 圖案 × 配色 × 版本。
   * 基底：御守、繪馬、團扇、手拭巾、壓克力立牌、徽章、T 恤、玩偶、馬克杯、明信片、扭蛋。
   * 圖案：樂園吉祥物（開局從狐狸／狸貓／招財貓／白蛇選一）、工作人員角色、設施插畫、季節圖案。
   * 版本：一般／季節限定／活動限定／數量限定。
   * 生命週期：新品話題度高、隨時間下降；限定品帶動收藏型客人回訪。
3. **合作商品**：一律為**架空**品牌與作品（不使用真實 IP）。在地店家、架空動畫、架空偶像、其他觀光地、鐵道公司。
   流程：洽談（知名度／好感度門檻）→ 簽約（分潤、期間）→ 開發 → 合作活動 → 結算。

## 8. 人物呈現（🧪 技術驗證樣本：`dist/ennichi/index.html`）

依使用者指定採用**混合方案（LOD）**：

| 距離／用途 | 呈現 | 技術 |
|---|---|---|
| 特寫、劇情、跟拍 | 高精度 VRM | `three-vrm`：MToon 卡通著色、貼圖五官（眼睛／眼皮／嘴巴面片）、表情（blink／happy／aa）、彈簧骨（馬尾、大袖） |
| 中景客人 | 換裝 VRM（同骨架，換材質顏色／零件） | 同上，關閉彈簧骨以省效能 |
| 遠景群眾 | **看板人物（billboard）** | 開場時把 VRM 從 8 個方向 × 4 格走路姿勢**即時渲染成圖集**，再以 `InstancedMesh` 一次畫出全部客人（1 draw call） |
| murmur、對話 | 2D 立繪 | jikan 照片沿用＋新製立繪 |

* 看板人物和 VRM 用同一個模型產生，所以風格一致；換裝顏色＝圖集裡多一列。
* 方向選擇：客人朝向 − 鏡頭方位角，四捨五入到 45°。

### 8.1 模型（🧪 第 2 版：臉型與服裝細緻化，2026-11-12）

樣本使用 `tools/ennichi_model/build_vrm.js` **程式產生**的模型（巫女小夜），完全符合 VRM 1.0
（`VRMC_vrm`＋`VRMC_materials_mtoon`＋`VRMC_springBone`），約 15,500 頂點、1 MB。

* **臉型**：球體雕塑成下巴收尖的臉（下半臉往下巴收窄、正面稍平、後腦飽滿、下巴微尖）＋小鼻樑＋耳朵。
* **五官**（與 VRoid 相同的作法）：
  * 眉、腮紅、鼻影畫在臉部貼圖（512²，正面投影）。
  * 眼睛、眼皮、嘴巴是貼著臉表面的小面片（貼圖＋`alphaMode: MASK`）。
  * 眼睛大小：寬約 0.044（臉寬約 0.30）——使用者指定「不要動畫式特大，但要清楚可見」。
  * 眨眼／笑眼＝皮膚色、下緣是睫毛的**眼皮面片往下滑**（`blink` 中央多滑、`happy` 兩端多滑成 ^），眼睛壓扁藏到眼皮後；`aa`＝嘴巴面片拉開。
* **頭髮**：頭頂髮殼＋11 束瀏海、耳前側髮、後髮 7 束、馬尾 5 束（沿曲線掃掠、尾端收尖），馬尾有 4 節彈簧骨。
* **服裝**：白衣的交領（左衽在上）＋紅色襦袢領、緋袴的褶（打褶的旋轉體，前深後淺）、腰紐繞一圈＋前結（兩圈兩垂帶）、腰板、
  大袖（每側 3 條彈簧骨鏈，輕微擺動）＋紅色袖括紐、白足袋＋草履（紅鼻緒）、丈長＋水引的髮結。
* 注意：
  * 袖子的彈簧骨**不接碰撞球**（手放下時支點貼著身體，碰撞球會把袖子推得扭曲），重力也只給 0.25。
  * 皮膚的 MToon 陰影色要淡（`#f4d0c6`）、不加邊緣光，否則夜景大半在陰影裡，整張臉會變橘紅。
  * 看板圖集每拍一格都要先 `springBoneManager.reset()`，否則轉向後馬尾會被甩歪。

### 8.2 讓模型更細緻的做法比較 ❓

| 做法 | 臉型 | 服裝 | 成本 | 適用 |
|---|---|---|---|---|
| **程序化＋貼圖**（目前樣本） | 中：雕塑球體＋貼圖五官 | 中：交領、褶、結都能做，但沒有布料皺褶 | 程式可重產、可參數化換裝 | 群眾、換裝變體、原型 |
| **VRoid Studio** → VRM | 高：臉型滑桿、眼睛／眉毛等都可細調，動漫風最自然 | 高：服裝模板＋自己畫貼圖（和服花紋、袴的褶可用貼圖表現） | 每位角色數小時，免費 | **主要角色（推薦）** |
| **Blender**＋VRM Add-on | 最高：自由雕刻 | 最高：可做布料模擬後烘成形狀、法線貼圖皺褶 | 需要建模技能，最耗時 | 招牌角色、特殊服裝 |
| AI 圖生 3D（從立繪產生）→ 自動綁骨 → Blender 轉 VRM | 不穩：動漫臉常變形 | 中〜高：外型細節多，但拓樸亂、難做表情 | 快，但要大量修整 | 道具、雕像、吉祥物（不建議用於角色） |

建議：主要角色（小夜、鐵子、蓮華…）用 VRoid 做，直接替換 `static_src/models/ennichi/<id>.vrm`；
客人群眾與服裝變體繼續用程序化模型（或從 VRoid 模型換貼圖）烘成看板圖集。

* 授權：自製模型的 VRM meta 填 `personalNonProfit`、禁止再散布；若改用他人模型，必須確認其 VRM meta／VRoid Hub 條件允許「網頁遊戲內使用」。

### 8.3 立繪

* 一律沿用 jikan（256×256 webp）。分配見 §3.1；常客「小雛」= `n_025`。
* jikan 有部分頭像較為暴露；緣日樂園是全年齡的樂園經營，只挑不暴露的。

## 9. 技術

### 9.1 three.js 版本與擴充（🧪 已驗證 2026-11-12）

* 全站共用 `static_src/vendor/three.min.js` = **r149**（UMD，全域 `THREE`）。
* r148 起官方不再提供 `examples/js`（UMD 版 GLTFLoader 等），因此以 esbuild 把以下模組打包成一支 IIFE，
  並把其中所有 `import "three"` 指向全域 `window.THREE`：
  * three@0.149.0 `examples/jsm`：`GLTFLoader`、`OrbitControls`、`EffectComposer`、`RenderPass`、`UnrealBloomPass`、`ShaderPass`、`GammaCorrectionShader`、`BufferGeometryUtils`
  * `@pixiv/three-vrm` **3.5.5**（peer 依賴宣告為 `three >= 0.137`）
* 產物：`static_src/vendor/ennichi_vrm.js`（約 227 KB），全域 `window.PriTestEnnichiVendor`。重建方式見 `tools/ennichi_vendor/build_vendor.js`。
* 驗證結果：r149 ＋ three-vrm 3.5.5 可以載入 VRM 1.0；MToon、描邊、表情 morph、彈簧骨、`getNormalizedBoneNode` 皆正常。
* **不升級**全站的 three.min.js：其他遊戲都依賴 r149 的 API（`outputEncoding` 等），升級風險大；ennichi 只多載一支擴充。
* 注意：r149 用 `renderer.outputEncoding = THREE.sRGBEncoding`（不是新版的 `outputColorSpace`）；用 EffectComposer 時最後要加 `GammaCorrectionShader`。

### 9.2 畫面

* Bloom（`UnrealBloomPass`）：燈籠、攤位招牌、摩天輪燈飾的夜景發光。
* 低階裝置：畫質「低」時關閉 Bloom 與描邊、降低看板人物數量。📝

### 9.3 正式版預計使用 📝

| 技術 | 用途 |
|---|---|
| Blender Python 程序化建模 → `.glb` | 鳥居、燈籠、攤位、設施（參數化，可重新產生） |
| Draco／Meshopt 壓縮 | 縮小 `.glb`（需在 vendor 加對應 decoder） |
| `LatheGeometry`／`ExtrudeGeometry`／`TubeGeometry` | 燈籠、招牌、雲霄飛車軌道（玩家拉線） |
| `InstancedMesh` | 群眾、燈籠串、樹木 |
| 粒子 | 櫻花、螢火蟲、雪、煙火 |
| 延遲載入 | 只在需要時下載某區的模型與角色 VRM |

### 9.4 容量預算

`static_src/images` 已約 230 MB，GitHub Pages 網站上限 1 GB。ennichi 目標 ≤ 60 MB：
主要角色 VRM 8 × ≤ 8 MB、客人換裝零件 ≤ 10 MB、建築 `.glb`（壓縮後）≤ 15 MB、立繪 ≤ 5 MB。
