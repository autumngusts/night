# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static-site GM/player companion tool for a tabletop RPG ("夜渡り" / Elden Ring Nightreign TRPG), plus a home page that can host other mini-projects (`site_src/projects.py`). Python generates static HTML at build time; all actual game logic runs client-side in vanilla ES5 JavaScript and persists to `localStorage` (with optional Firebase Realtime Database sync for "cloud" games). There is no build framework (no npm/webpack) and no automated test suite — verification is manual (browser click-through) or via ad-hoc Playwright scripts against the built `dist/`.

## Commands

```bash
python generate.py      # builds dist/ from site_src/ + static_src/ (must re-run after any source edit)
python -m http.server 8000 --directory dist   # serve dist/ locally to test in a browser
```

On Windows, use `py -3 generate.py` if `python` isn't on PATH.

There is no lint/test command — nothing is configured. `node --check static_src/<file>.js` is useful as a quick syntax gate before rebuilding a large JS file. Pushing to `main` triggers `.github/workflows/deploy.yml`, which runs `python generate.py` and deploys `dist/` to GitHub Pages — the built output is never committed (`dist/` is gitignored).

### Manual verification

Since there's no test harness, the working pattern for verifying JS changes is: rebuild, serve `dist/` locally, then drive it with a throwaway Playwright script (not checked in) that navigates the real UI and/or reads `window.PriTest*` globals plus `localStorage` directly. Two things trip this up reliably:
- The admin page (`admin/index.html`) gates everything behind `window.prompt("password")` (hardcoded `"night"`, see `games.js`) — a Playwright script needs a `page.on("dialog", ...)` handler that accepts prompts with `"night"`, or every admin action hangs (including the *whole page*, since `requireAdmin()` redirects to `../index.html` on a rejected/null prompt — a script missing the dialog handler fails with `window.PriTestGames is undefined` on the *next* line, not an obvious "prompt" error).
- To create a game from a script: call `window.PriTestGames.create(name, scenarioId, storageMode)` from the admin page context (`storageMode: "local"` for a script-created game) — the exported name is `create`, not `createGame`. `night/index.html` (and `characters/index.html`) redirect straight back to `../index.html` if loaded without a valid `?game=<id>` in the URL, silently skipping all their `<script>` tags — always create the game first, then navigate with the id in the query string.
- Writing a hand-rolled/partial state object into `pritest-night-state-<gameId>` *before* the first real page load causes the app to silently fall back to defaults for the fields you didn't set. Prefer: let the app build a real state through normal UI actions first, then read-modify-write only the specific fields you need via `localStorage`, then `page.reload()`.
- To find a real weapon/item id for a test fixture, use `window.PriTestWeapons.list()` (a flat array, each entry has a `.category` string) — not `Weapons.categories()[i].items`, which doesn't exist; categories only hold rules metadata (`basicStats`, `innateSkills`), not the weapon instances themselves.

## Architecture

### Build pipeline

`generate.py` does two things: (1) copies `static_src/*.js` and `style.css` verbatim into `dist/static/`, and stamps `static_src/i18n.template.js` → `dist/static/i18n.js` by substituting `__I18N_DATA__` with the JSON-serialized `STRINGS` dict from `site_src/i18n_data.py`; (2) calls each `site_src/*_page.py`'s `build_*_html()` to produce `dist/{index,night,admin,admin/scenarios,characters}/index.html`. Every page shares one shell (`site_src/layout.py`'s `page_shell`) — header, language switcher, footer script tags — and pages are otherwise independent HTML documents (no client-side router).

To add a new mini-project page: add `site_src/<name>_page.py` with a `build_*_html()`, register it in `generate.py`'s `build_pages()`, add an entry to `site_src/projects.py`, and add its i18n keys to `site_src/i18n_data.py`.

### i18n

All user-facing strings live in one place: `site_src/i18n_data.py`'s `STRINGS` dict, keyed by language (`zh`/`ja`/`en`) then by string key. `zh` is the default/fallback language. Static HTML elements pick up strings automatically via `data-i18n="key"` attributes (applied by `i18n.template.js`'s `applyI18n()`); JS-generated content calls `window.I18N.t(key, params)` with `{param}`-style interpolation. Data modules (character types, weapons, enemies, etc.) instead store bilingual text directly as `{ja, zh}` objects (built with a local `C(ja, zh)` helper in each file) and pick the current language at render time — `en` is largely unauthored for game data and falls back to `ja`.

### Client-side module map (`static_src/*.js`)

All modules are IIFEs that attach a namespace to `window` (e.g. `window.PriTestGames`, `window.PriTestCharacterDrawer`). Load order matters and is defined once in `generate.py`'s copy list / each page's `extra_scripts`.

- **Infrastructure**: `i18n.template.js` (→ `i18n.js`), `games.js` (game CRUD, admin password gate, import/export/share via base64url-encoded JSON, QR sharing), `game_storage.js` (cloud sync — a no-op abstraction layer unless a game's `storageMode === "cloud"`, in which case it lazy-loads the Firebase SDK, activates App Check, and mirrors state to Realtime Database), `firebase_config.js` (Firebase project config + `PRITEST_APPCHECK_SITE_KEY`, both plaintext client-side values — normal for Firebase, not secrets), `qrcode.js` (vendored).
- **Reference/rulebook data** (mostly static bilingual content, no page-specific logic): `character_types.js`, `weapons.js`, `weapon_rulebook.js`, `talismans.js`, `consumables.js`, `enemies.js`, `fields.js` (map/board cards), `event_rulebook.js`, `night_bosses.js` + `night_boss_rulebook.js`, `worldview.js`, `scenarios.js` (fixed card layouts per scenario).
- **Page logic**: `admin.js` / `admin_scenarios.js` (game list + scenario/card-deck editor), `characters.js` (character roster/gallery page), `character_drawer.js` (huge — the shared character-detail/stat-computation module, see below), `night.js` (huge — the actual play-session engine, see below).

#### Firebase security (Realtime Database + App Check)

`database.rules.json` (deploy via `firebase deploy --only database` or paste into the console's Rules tab — **not done automatically by `generate.py` or the GitHub Actions deploy**, must be pushed to Firebase separately) restricts `games/$gameId` to authenticated reads/writes with `$gameId` matching the app's own ID format (`^g[0-9a-f]{32}$`) and rejects unknown child keys; it deliberately does *not* try to enforce per-owner write access, since any client holding the (unguessable, 128-bit) `gameId` is the intended access model — a party's players and the GM all write to the same game with no individual accounts. `game_storage.js` additionally activates Firebase App Check (`firebase-app-check-compat.js`, reCAPTCHA v3, site key in `firebase_config.js`) purely to block non-app clients that copy the public Firebase config and hit the API directly — this is a defense against abuse/quota-drain, not an access-control mechanism, and has no effect while `PRITEST_APPCHECK_SITE_KEY` is empty. `.github/CODEOWNERS` + branch protection on `main` (GitHub-side, not in this repo) require PRs from anyone but the repo owner, who can still push directly.

### `character_drawer.js` — shared character model & stat math

Owns character CRUD (`newCharacter`, stat steppers), and every damage/bonus computation: `computeArtPower` (the central power-modifier calculation — combines the character type's base `powerMod`, talisman bonuses, and relic-effect bonuses; feeds into both weapon-attack damage and skill/sorcery/incantation damage so a fix here is automatically reflected everywhere), `computeWeaponDamage`, talisman/relic/attached-effect bonus helpers (`talismanFlatMaxStatBonus`, `relicFlatMaxStatBonus`, `attachedFlatMaxStatBonus`, `totalFlatMaxStatBonus`, etc.). It's used by both `characters.js` (character creation/roster, no live game state) and `night.js` (during play), so anything that depends on live combat state (position, aggro) is exposed defensively — e.g. `night.js` sets `window.PriTestNightBattleContext`, and `character_drawer.js` checks `window.PriTestNightBattleContext && ...` rather than assuming it exists.

Characters have three distinct, independently-tracked bonus systems that look similar but are separate arrays on the character object and must each be checked when computing any "total" stat: `learnedRelicEffects` (type-specific, keyed `"<typeId>-r<group>-<index>"`, gated by character level via `relicMaxLearnable`), `learnedAttachedEffects` (a small fixed universal set, rolled via 2d6, capped at `MAX_ATTACHED_EFFECTS`), and `talismanIds` (equipped decorations, each with a single passive effect).

### `night.js` — play-session engine

The state machine for an actual session: dice pools, action/extra/defense phase transitions, the front/back-row battle board, combat modal (attack/skill/defense/flask/consumable/move/equip tabs), enemy HP tracking, turn rewards, event chips, near-death/revival. All state lives in one `state` object persisted to `localStorage["pritest-night-state-<gameId>"]` on every mutation (`saveState()`); characters are persisted separately to `localStorage["pritest-characters-<gameId>"]` (`saveRosterCharacters()`).

**Before touching enemy HP rows, guard/stagger, or attribute/ailment buildup**, read `docs/enemy_damage_rules.md` — a rulebook transcription (damage-notation grammar, the 5-priority order for applying damage to an enemy, the Guard Count / Guard Reduction / HP-value formula, attribute/ailment thresholds) plus a table of what's already implemented here vs. still missing. As of 2026-08-09 the Guard Count/HP-value system itself is implemented (`applyGuardedDamageToEnemy`, `#battle-guard-calc-block`) for regular enemies and two Night Lords (gladius/maris); Gladius's split-form 3-way HP division and its auto form-transition are **not yet wired into code**.

**Before touching scenario/field-card flow, floor breakthrough checks, field movement, or event chips**, read `docs/scenario_flow_rules.md` — a rulebook transcription of the full session flow (the day1→day2→day3 step sequence, the field/floor exploration sub-steps, field movement/adjacency/climbing checks, event chip resolution) plus an implementation-status table. As of 2026-08-09 breakthrough/climbing checks auto-roll dice and auto-compute the target number but never auto-decide pass/fail (GM clicks a Pass/Fail button); event chip placement and the 靈脈/祝福/商人 chips are fully automated, 強敵/隨機 chips and the `varianceTable` branch-selection system are not.

**Before touching turn/phase progression, front/back positioning, aggro, Time Loss / roll-effect tiers, or combat-start/end procedures**, read `docs/combat_flow_rules.md` — a rulebook transcription of the battle-section flow (action/extra/defense/end phase sequence, front/back area rules, combat-start public/private info, normal vs. simplified combat, boss vs. mob combat, pre/post-combat procedures) plus an implementation-status table. Confidence is lower than the other two docs in this repo (several sections come from blurry photos and are flagged inline with ✗) — verify against the physical rulebook before relying on exact wording. As of 2026-08-09 phase state (`state.actionPhase`), front/back/aggro, guard-break, and the Time Loss/roll-effect tier system (`TIME_LOSS_ROW_DEFS`, `ROLL_EFFECTS`) are implemented; the normal-vs-simplified-combat distinction and automatic boss-vs-mob level comparison are not.

Three placeholder symbols recur throughout combat/relic/talisman/consumable text and are load-bearing for damage math — get them wrong and numbers silently come out incorrect (or get fabricated) rather than erroring:
- `□` (hollow square) = a literal, auto-computable amount: `+1` per box in a *cap/max* context (e.g. `最大HP+□□□` = `+3`, parsed by `sumMaxStatDeltaFromText`), or `+1` per box in a one-shot *heal* context (e.g. `HP回復：□□` = heal `2`, parsed by `countHealSquares`). Always resolve these to a real number.
- `▲` / `◆` in a damage line (e.g. `總合傷害：50+▲`) is a placeholder for the character's own power-modifier contribution, resolved via `computeArtPower`/`fixedSkillPowerValue` rather than being a literal number — don't treat it as text to strip, it's meaningful to the formula. **Same two symbols, different meaning in a `【追加効果】` (additional-effect) field**: there `▲` = 0.5 and `◆` = 1 "Guard Reduction" point (ガード削り値), unrelated to power-modifier — see `docs/enemy_damage_rules.md` §2/§5 before writing any code that touches either meaning.
- `■` (filled square) is the one genuinely ambiguous case: it marks a value the rulebook leaves context-dependent (a specific weapon's HP-value, an amount that depends on a die the GM already rolled elsewhere, a mob's fixed-but-untracked HP chunk) and this app **never invents a number for it** — the established, consistent pattern across every relic/attached-effect/consumable handler in `night.js` is to push the effect's own rulebook body text into the action-log `lines` array as a reminder and let the GM apply it manually (see any `findLearnedRelicEffectByName(...)` call whose result is only used to `lines.push(CharacterTypes.localizedText(effect.body))`, or the `consumable_effect_*_note` i18n keys). Do not add arithmetic for `■` — if a future rule turns out to have a fixed value, that's a data problem to fix in `character_types.js`/`consumables.js`'s body text (e.g. give it real `□`s), not a reason to hardcode a guess in JS.

Many special per-ability behaviors (unique buffs, alternate action modes granted by a specific relic effect, position-locked or resource-gated skills) are hooked by checking `entry.id` inside `night.js`'s combat rendering functions (`renderCombatSkillAction`, `renderCombatDefenseAction`) rather than being data-driven — when a relic/talisman effect needs to change *how* a skill behaves (not just add a flat number), the established pattern is to synthesize a fake ability entry (same shape as a `character_types.js` ability: `{id, kind, name, body}`, see `CRUCIBLE_BEAST_ACTIONS` for the template) and conditionally concat it into the entries list so it flows through the existing generic cost/damage-parsing pipeline instead of being hand-coded.

### "Until end phase" effects: the phase-reset checklist

A large fraction of relic effects, attached effects, and consumables are worded "直到結束階段為止" (until end phase) — a self- or party-wide buff/flag that must vanish the instant the action/extra/defense phase changes, not just at battle end. The established mechanism is a plain boolean/number field on the character object, named `c._xxxActive` or `c._xxxUntilEndPhase`, that some action's confirm handler sets and that a damage/bonus helper function (`heroMeatHitBonus`, `finaleAttackBuffBonus`, `ominousStrikeHitBonus`, etc. — all living near each other above `computeSkillDamage`) reads. **The field is only half the feature**: `setActionPhase()` has one `rosterCharacters.forEach(...)` loop, run on *every* phase transition, that explicitly resets every one of these fields back to `0`/`false`/`null`. Adding a new "until end phase" effect without adding its reset line there is the single most common way to introduce a bug in this codebase — the buff will silently outlive the phase it was meant for. The same function also has a `battle`-wide equivalent for effects that persist across an entire *round* instead of just a phase (`_wingsOfSalvationActive`-style flags, cleared only on a fresh combat-phase entry from defense) — check which lifecycle a given effect's rulebook wording actually implies before picking which reset site to use.

### Relic effects that require the player to choose a target (element/ailment/weapon)

Several relics say "習得此遺物效果時選擇1種屬性/異常" (choose one when learned) — e.g. `屬性蓄積值＋1`, `屬性達成的歡喜`, `異常狀態達成的歡喜` in `character_drawer.js`. These are handled by `RELIC_CHOICE_CONFIG_BY_NAME` (maps the relic's zh/ja name to `{field, options}`) plus `assignRelicChoiceIfNeeded(c, effect, pickedOption)`: the learn-candidate card renders a `<select>` (default option = "decide randomly") right next to the "習得" button, and the resulting choice — or, if left on the default, a random pick — is stored on `c[field]` (e.g. `c.relicAccumElementChoice`). The learned-effects list re-renders the same `<select>` so the choice can be changed later. Anything in `night.js` that needs to know "which element/ailment did this character pick" just reads `c.relicAccumElementChoice` / `c.relicJoyElementChoice` / `c.relicJoyAilmentChoice` directly (compare against both `.zh` and `.ja` of whatever label you're matching, since accumulation labels/log text aren't always in the same language as the stored choice). The equivalent for the universal attached-effects (`status_resist`/`element_resist`) is the older, random-only `assignAttachedResistChoiceIfNeeded` — it was never upgraded to a picker UI because those two aren't blocking anything else; if you touch them, prefer bringing them in line with `RELIC_CHOICE_CONFIG_BY_NAME` rather than adding a third pattern.

### Consumables (`consumables.js` + `night.js`'s `applyConsumableEffect`)

`consumables.js` is pure reference data (name/body text only, like the other rulebook modules) — it has no effect logic. Every consumable's actual mechanical effect lives in `night.js`: `CONSUMABLE_TARGET_KIND` maps each item id to how its target is chosen (`self`, `enemy` — reuses the attack action's `resolveSelectedEnemyOptions()`/`combatAttackTargetEnemyKey` — `otherPc`, `ailment` — filtered to whatever the user has actually accumulated via `state.battle.attributeStatus.received` — `grease`, or `allPc`), `renderCombatConsumableAction` renders the matching picker, and `applyConsumableEffect(c, itemId, applyLevel2, target)` is the single dispatch point that actually mutates state and returns `{total, lines}` for the action-log box. `applyLevel2` (a consumable's "等級2效果", gated in the rulebook on some other unrelated condition being met) is only auto-applied when the user has 學者's `carried_knowledge` ability (which the rulebook says always triggers level-2 effects); otherwise the level-2 text is pushed into `lines` as a GM reminder, never applied. Consumable "塗脂" (weapon/shield grease) is the one with the most moving parts — it sets `c._greaseWeaponId`/`c._greaseElementRef` (read by `weaponAccumulationEffects` to synthesize a temporary attack-accumulation skill, and by `relicEffectAppliesTo`'s `武器脂的達人` case to gate the flat hit-damage bonus) or `c._greaseShieldId` (read alongside `c._guardValueBonusUntilEndPhase` in the defense/guard confirm handler) — all reset in the same phase-reset loop described above. If you add a 17th consumable, follow this same three-piece pattern (target-kind entry, any bespoke picker UI, one `else if` branch in `applyConsumableEffect`) rather than inventing a new mechanism.
